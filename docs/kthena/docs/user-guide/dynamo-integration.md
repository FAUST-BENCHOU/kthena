# Integrate Dynamo with Kthena

This guide shows how to run
[NVIDIA Dynamo](https://github.com/ai-dynamo/dynamo) multinode workloads with
Kthena. Dynamo continues to create standard `LeaderWorkerSet` (LWS) resources,
while Kthena reconciles those resources into `ModelServing` workloads.

The integration follows this control-plane path:

```text
DynamoGraphDeployment
  -> DynamoComponentDeployment
  -> LeaderWorkerSet
  -> Kthena ModelServing
  -> Volcano PodGroup
  -> Pods
```

Kthena preserves the LWS behavior that Dynamo's distributed runtimes observe:

| Contract | Behavior                                                   |
| -------- | ---------------------------------------------------------- |
| Runtime  | Injects the standard `LWS_*` environment variables         |
| DNS      | Provides LWS-compatible hostnames and shared-subdomain DNS |
| Status   | Projects replica counts and LWS conditions                 |
| Service  | Recreates the LWS headless Service after deletion          |

## Prerequisites

- Kubernetes 1.30 or later.
- Helm 3.
- [Volcano](https://volcano.sh/en/docs/installation/) installed for gang
  scheduling.
- Kthena installed with the workload controller and its webhook enabled. See
  the [Kthena installation guide](../getting-started/installation.md).
- A Dynamo runtime image and the accelerator resources required by the selected
  inference backend for a production deployment.

The following versions were used for validation. Replace them with another
compatible combination if needed.

### Validated versions

| Component  | Version |
| ---------- | ------- |
| Kubernetes | v1.31.0 |
| Dynamo     | v1.4.2  |
| LWS CRD    | v0.10.0 |
| Volcano    | v1.15.2 |

Other compatible versions may work; follow Dynamo's current LWS requirements.

:::warning
Install only the LWS CRD. Do not install the native LWS controller or webhook
in the same cluster because Kthena owns reconciliation of these LWS resources.
:::

## Install the integration dependencies

Install the LWS CRD before starting Kthena and Dynamo so both controllers can
discover the API:

```bash
export LWS_VERSION=v0.10.0

kubectl apply --server-side -f \
  https://raw.githubusercontent.com/kubernetes-sigs/lws/${LWS_VERSION}/config/crd/bases/leaderworkerset.x-k8s.io_leaderworkersets.yaml
```

Install Volcano if it is not already present:

```bash
helm repo add volcano-sh https://volcano-sh.github.io/helm-charts
helm repo update
helm upgrade --install volcano volcano-sh/volcano \
  --namespace volcano-system \
  --create-namespace
```

Install Kthena by following the
[installation guide](../getting-started/installation.md). The workload webhook
is enabled by default; keep `workload.controllerManager.webhook.enabled=true`
because it defaults fields on the LWS resources generated by Dynamo.

Install the Dynamo platform without enabling Grove or KAI Scheduler:

```bash
export DYNAMO_NAMESPACE=dynamo-system
export DYNAMO_RELEASE_VERSION=1.4.2

helm fetch \
  https://helm.ngc.nvidia.com/nvidia/ai-dynamo/charts/dynamo-platform-${DYNAMO_RELEASE_VERSION}.tgz
helm upgrade --install dynamo-platform \
  dynamo-platform-${DYNAMO_RELEASE_VERSION}.tgz \
  --namespace "${DYNAMO_NAMESPACE}" \
  --create-namespace
```

See the Dynamo
[installation documentation](https://github.com/ai-dynamo/dynamo/blob/main/docs/fern/pages/kubernetes/installation/install-dynamo.md)
for registry credentials and release-specific options.

Verify that there is only one controller responsible for LWS resources:

```bash
kubectl get crd leaderworkersets.leaderworkerset.x-k8s.io
kubectl get deployments --all-namespaces | grep -E 'kthena|dynamo|leaderworker'
```

The output should include the Kthena and Dynamo controllers, but not a native
LWS controller.

## Deploy a Dynamo workload

Use a `DynamoGraphDeployment` with a multinode worker component.
`multinode.nodeCount` marks the component as multinode. With the LWS and Volcano
APIs installed, the annotation below disables the Grove pathway so Dynamo
renders the component as a `LeaderWorkerSet`. The following fragment declares a
two-node component:

```yaml
apiVersion: nvidia.com/v1beta1
kind: DynamoGraphDeployment
metadata:
  name: multinode-model
  namespace: dynamo-demo
  annotations:
    nvidia.com/enable-grove: 'false'
spec:
  backendFramework: sglang
  components:
    - name: Frontend
      type: frontend
      replicas: 1
      podTemplate:
        spec:
          containers:
            - name: main
              image: <dynamo-runtime-image>
    - name: decode
      type: decode
      replicas: 1
      multinode:
        nodeCount: 2
      podTemplate:
        spec:
          containers:
            - name: main
              image: <dynamo-runtime-image>
              command:
                - python3
                - -m
                - dynamo.sglang
              args:
                - --model-path
                - <model>
```

Add the model, storage, GPU, networking, and backend arguments required by your
Dynamo runtime image. Refer to Dynamo's
[multinode orchestration guide](https://github.com/ai-dynamo/dynamo/blob/main/docs/fern/pages/kubernetes/installation/multinode-orchestration.md)
and backend examples for a complete production manifest.

Apply the manifest after creating its namespace:

```bash
kubectl create namespace dynamo-demo
kubectl apply -f dynamo-graph-deployment.yaml
```

## Verify the integration

Check the complete resource chain:

```bash
kubectl get dynamographdeployments,dynamocomponentdeployments \
  -n dynamo-demo
kubectl get leaderworkersets,modelservings,podgroups \
  -n dynamo-demo
kubectl get pods -n dynamo-demo -o wide
```

A ready deployment has all of the following properties:

- The `DynamoGraphDeployment` reports `Ready=True`.
- Its `DynamoComponentDeployment` resources report `Available=True`.
- The multinode `LeaderWorkerSet` reports the expected `READY` and `UP-TO-DATE`
  replica counts and `Available=True`.
- The corresponding `ModelServing` reports the expected replica, available,
  and updated counts.
- Its Volcano `PodGroup` is `Running` and all leader and worker Pods are ready.

Inspect the LWS runtime environment in a leader and worker Pod:

```bash
kubectl exec -n dynamo-demo <leader-pod> -- env | grep '^LWS_'
kubectl exec -n dynamo-demo <worker-pod> -- env | grep '^LWS_'
```

For a two-node group, both Pods receive the same `LWS_LEADER_ADDRESS` and
`LWS_GROUP_SIZE=2`; the leader receives `LWS_WORKER_INDEX=0` and the worker
receives `LWS_WORKER_INDEX=1`.

Check the shared headless Service and Pod network identities:

```bash
kubectl get service -n dynamo-demo <lws-name> -o yaml
kubectl get pods -n dynamo-demo \
  -l leaderworkerset.sigs.k8s.io/name=<lws-name> \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.hostname}{"."}{.spec.subdomain}{"\n"}{end}'
```

The Service has `clusterIP: None` and `publishNotReadyAddresses: true`. Leader
and worker DNS identities use the following shared-subdomain form:

```text
<lws-name>-0.<lws-name>.<namespace>
<lws-name>-0-1.<lws-name>.<namespace>
```

This identity also supports Dynamo TRT-LLM's worker-host derivation from the
leader address.

## CPU-only control-plane validation

The compatibility path can be checked without GPUs by replacing the frontend
and worker images with a small HTTP server while retaining a command marker
that Dynamo recognizes as SGLang. This validates resource reconciliation,
runtime-variable expansion, DNS, status propagation, and Service recovery. It
does not validate model loading or inference. The manifest was validated with
the Dynamo release listed above and is intended only for control-plane testing.

<details>
<summary><b>dynamo-kthena-smoke.yaml</b></summary>

```yaml
apiVersion: nvidia.com/v1beta1
kind: DynamoGraphDeployment
metadata:
  name: kthena-lws-smoke
  namespace: dynamo-demo
  annotations:
    nvidia.com/enable-grove: 'false'
spec:
  backendFramework: sglang
  components:
    - name: Frontend
      type: frontend
      runtimeVersionOverride: '1.4.2'
      replicas: 1
      podTemplate:
        spec:
          containers:
            - name: main
              image: registry.k8s.io/e2e-test-images/busybox:1.36.1-1
              command: [/bin/sh, -c]
              args:
                - >-
                  mkdir -p /tmp/www; : > /tmp/www/live; : > /tmp/www/health;
                  exec httpd -f -p 8000 -h /tmp/www
    - name: decode
      type: decode
      runtimeVersionOverride: '1.4.2'
      replicas: 1
      multinode:
        nodeCount: 2
      podTemplate:
        spec:
          containers:
            - name: main
              image: registry.k8s.io/e2e-test-images/busybox:1.36.1-1
              command: [/bin/sh, -c]
              args:
                - >-
                  mkdir -p /tmp/www; : > /tmp/www/live; : > /tmp/www/health;
                  printf '%s\n' "$0" > /tmp/www/runtime-contract;
                  env | sort > /tmp/www/env;
                  exec httpd -f -p 9090 -h /tmp/www
                # Testing only: this second argument becomes $0 for `sh -c`.
                # It keeps the SGLang marker without starting SGLang.
                - python3 -m dynamo.sglang
```

</details>

## Compatibility scope

- The integration implements LWS's default shared-subdomain network identity.
  `networkConfig.subdomainPolicy: UniquePerReplica` is not supported.
- Do not run the native LWS controller or webhook alongside Kthena.
- The Kthena workload webhook must remain enabled for Dynamo-generated LWS
  resources.
- A CPU-only smoke test validates the control-plane contract, not the GPU data
  plane, model inference, RDMA, or backend-specific performance.

For an overview of Kthena's LeaderWorkerSet integration, see
[LeaderWorkerSet integration](./lws-integration.md).
